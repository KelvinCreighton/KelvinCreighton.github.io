MapReduce Library

CMPUT 379: Operating System Concepts • University of Alberta

View Source on GitHub

I built a reusable MapReduce library in C, then used it to write a word count program. The framework accepts mapper and reducer callbacks, routes emitted key and value pairs into partitions, and lets each reducer consume the values for its keys.

CPOSIX threadsThread poolsHash partitioningMutexes and condition variablesMapReduce callbacks

A framework built around callbacks

The public API is built around four functions. MR_Run() coordinates mapping and reducing, MR_Emit() stores each key and value pair, MR_Partitioner() chooses a partition for a key, and MR_GetNext() returns values for a key to the reducer. That separation lets an application define its own map and reduce work without managing the framework's queues and partitions directly.

In the word count example, the mapper reads a file and emits each token with the value 1. The reducer repeatedly requests values for one key, counts them, and appends the result to a file named for its partition.

Scheduling and partitioning work

I implemented a pthread job queue for mapper and reducer work. Mapper jobs use input file size as their priority; reducer jobs use the number of values in a partition. The queue inserts jobs in ascending priority order. Mutexes protect queue state and the shared partition table, while a condition variable is used to coordinate the end of each phase.

MR_Emit() hashes each key with a DJB2 style hash to select a partition. It copies the key and value into a linked list kept in ASCII key order. During reduction, MR_GetNext() removes and returns one value for the requested key at a time, freeing the stored pair as it goes.

What I worked through

  • Separating application callbacks from the framework that schedules their work.
  • Protecting shared key and value data while multiple mapper jobs emit results.
  • Grouping values by key and consuming them safely during reduction.
  • Building and checking the library with compiler warnings treated as errors, pthread support, sample text files, and memory checking.

Scope and next steps

This implementation runs on one machine with POSIX threads. The library received 90/100. Course feedback gave full marks for runtime and memory use, but noted incorrect results on tests beyond the sample inputs. The worker routine also exits when it sees an empty queue instead of waiting for more jobs, so I would make the worker lifecycle reliable before claiming dependable parallel execution. I would then expand the tests to cover empty input, repeated separators, and a wider range of keys and partitions.
