CMPUT 379: Operating Systems

DragonShell

A Unix shell written in C. Processes, pipes, redirection, and signals, implemented through the operating system’s interfaces.

September 2024
View Source on GitHub

CMPUT 379: Operating System Concepts • University of Alberta

I built DragonShell in C to make operating system concepts concrete. A command entered at the prompt becomes a process; its file descriptors determine where data flows, and the shell must coordinate with the child program that runs it.

Implementing a shell with Unix system calls

For CMPUT 379, I wrote a small shell for Unix systems without relying on a shell library. I built the command loop, parsed each input line, separated commands built into the shell from external programs, and managed the processes and file descriptors needed to run them. I had to manage those mechanics myself, from starting a child process to deciding how its input and output reached the program.

I started with the prompt and commands for checking and changing directories. Next came external program execution, then output and input redirection and pipes. As those features began to interact, I returned to the parser, error handling, and process cleanup to make the pieces work together.

DragonShell supports cd, pwd, and exit as commands built into the shell. For external commands, the shell creates a child with fork(); the child configures its input and output, then calls execve(). The parent waits with waitpid() for foreground work, while an & command can run in the background.

Controlling process data flow

I implemented input and output redirection by opening the requested file and using dup2() to connect it to standard input or standard output. For a single pipeline, DragonShell creates a pipe and maps its file descriptors so one external command can provide input to the next. I also had to close descriptors that were no longer needed and handle missing files, missing commands, and incomplete redirection or pipe syntax.

The shell registers handlers for SIGINT and SIGTSTP, tracks foreground, background, and suspended process IDs, and cleans up tracked work when the user exits. On shutdown, it reports the user and system CPU time of child processes with getrusage().

What I worked through

  • Coordinating parent and child processes, including foreground waits and background execution.
  • Routing data through files and pipes by manipulating Unix file descriptors.
  • Tracking process state across signals and shell shutdown.
  • Testing the shell with commands built into it, external programs, redirection, pipelines, background work, and signal behavior; then checking process and memory behavior with system tools.

Scope and result

I kept the parser focused on the assignment. It separates arguments by spaces, invokes external programs by executable path, connects two commands with a pipe, and tracks one background process at a time. Within those limits, the project brings process creation, execution, waiting, I/O redirection, signals, and resource reporting together in one working program.

The assignment received 97/100. The grading feedback awarded full marks for the commands implemented in the shell, external command execution, CPU time reporting, background execution, redirection, piping, and signal handling. The recorded deductions were for a missing compile Makefile target and the README filename.
